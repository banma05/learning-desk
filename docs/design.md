# 学习台（开源版）设计

> 日期：2026-11-11
> 状态：已确认
> 标记：**【定】** = 作者明确定的；**【Claude 的判断】** = 作者交给 Claude 定的，可以推翻；没有标记的是从原版沿用的事实。
> 本文会随代码一起公开，所以不写原作者的雇主、项目、同事、本机路径。实施时要用到的私人信息（原版代码在哪、扫描词表）放在仓库外的本地备注里，见第九节。

---

## 一、为什么做

作者入职一个新项目后，自己搭了一个"学习台"：用 Claude Code 边聊边记，AI 按一份维护约定把弄懂的点、冒出的问题、每天做了什么直接写进一个 markdown 知识库，钩子在每次改动后自动生成一个离线网页并 git 提交。打开网页就能看到：项目懂了多少、哪块还空着、今天计划完成没有、有哪些问题要问谁。用了三周，觉得好用。

作者想把它开源到个人 GitHub，给别人用于**个人学习、新工作快速上手、快速了解一个项目**【定】。别人拿到后要**能直接用**，并且**附上教程**【定】。

## 二、目标、不做、做砸了

### 目标
- 一个从没见过它的人，照 README 大约十分钟搭好；第一次和 Claude 聊完，就能在网页上看到自己的第一篇笔记。
- 功能和原版一致，只去掉原作者的个人口径（见第六节）。原版现有功能：
  - 项目页：每个项目一张地图（骨架），大块的覆盖率、知识图谱；
  - 主题笔记和知识点（掌握程度按知识点汇总）；
  - 概念卡（跨项目通用的概念）；
  - 计划页：总计划 + 每天一个计划文件；
  - 工作表、成果表、问题表（问题按"问谁"分列）；
  - 全文搜索；阅读页（目录、"引用了我"、迷你图谱）；点状态复制一句话给 Claude 去改；
  - 两个 Claude Code 钩子：会话开始时报"今天到哪了"；改完文件自动重建网页并提交。

### 不做
- **不和作者自己的学习台共用代码，两份各管各**【定】。开源版不用兼容作者现有的数据，作者的知识库也不迁移过来。
- 不支持 Claude Code 以外的 AI 助手（钩子是 Claude Code 的机制）；但网页生成不依赖 AI，手动运行也能生成。
- 沿用原版：不做服务器、账号、多人共享、手机端。
- 不发布到 PyPI 之类的包仓库，clone 下来就能用【Claude 的判断】。
- 不做英文界面：文件名、格式字段、网页文字都是中文；README 开头加一段英文简介【Claude 的判断】。
- 不重写：原版代码可以由作者以个人名义开源，作者确认公司对此没有限制【定】，所以直接拿原版代码和测试改造。

### 做砸了的情况
- **仓库里出现原作者雇主的任何信息**：项目名、人名、表名、需求编号、内部网址、业务口径，包括 git 历史里【定，底线】。
- 使用者的私人笔记被推到公开仓库：比如使用者直接 clone 本仓库当自己的知识库，远程还指着公开仓库，一推就公开了。
- 安装脚本弄坏使用者已有的 Claude Code 设置。
- 钩子出错打断使用者的 Claude 会话（原版保证钩子永不打断会话，这一点要保住）。

## 三、约束

- Python ≥ 3.10（原版用到了 `X | None` 写法和海象运算符，所以不能更低）。除标准库外只依赖一个 `markdown` 库（原版就用它渲染 Markdown），写在 `requirements.txt` 里。作者本机只有 3.15，3.10 上的验证交给 GitHub Actions【Claude 的判断】。
- 生成的网页完全离线，不引用任何外部资源（CDN、字体、统计脚本）。
- Windows、macOS、Linux 都能用：代码里不写死路径，安装脚本用 Python 写。
- 所有文本文件 UTF-8、LF 行尾。
- 原版的 206 个测试全部带过来，改名后照样通过。
- **实施和验证过程中不能动作者本机真实的 Claude Code 设置**（`~/.claude/settings.json`、`~/.claude/CLAUDE.md`）：作者自己的学习台钩子就挂在那里，装第二套会让两套钩子同时触发。安装脚本要能指定一个临时的 Claude 设置目录来测试。

## 四、仓库长什么样【Claude 的判断】

```
<仓库名>/
├── README.md         是什么、一张截图、三个使用场景、十分钟上手
├── LICENSE           MIT
├── install.py        新建知识库 + 挂钩子（见第五节）
├── 模板/             新知识库的初始内容，安装时复制
│   ├── 维护约定.md   见第七节
│   ├── 学习台配置.json
│   ├── 问题.md  成果.md  工作.md     只有说明和表头
│   ├── 计划/总计划.md               可选，给一个空的结构示例
│   ├── 项目/  概念/                 空文件夹（各放一个说明文件）
│   └── .gitignore                   忽略生成的网页临时文件、hook.log、hook-status.json
├── 工具/             原版"工具/"改造后：build.py、hub/、hooks/
├── 示例/             填好的"网上书店"知识库，连同生成好的 学习台.html
├── tests/            原版测试，fixture 去掉原项目名
├── docs/
│   ├── 教程.md
│   ├── 格式说明.md
│   ├── design.md     本文
│   └── 截图/
└── .github/workflows/test.yml   Python 3.10 和最新版各跑一遍测试
```

测试放在顶层还是留在 `工具/tests/`、安装时复制哪些文件，由实施者定；要求是使用者的知识库里只有运行需要的文件，没有测试和 fixture。

## 五、使用者怎么装【Claude 的判断】

为什么挂在用户级设置、而不是只在知识库文件夹里生效：这个工具的价值在于"在别的项目里干活时顺手记"，所以钩子和维护约定要在每个 Claude 会话里都生效。原版就是这样挂的：
- `SessionStart` 钩子，matcher `startup|resume|compact|clear`，超时 15 秒；
- `PostToolUse` 钩子，matcher `Edit|Write|MultiEdit`，超时 60 秒，`async: true`；
- 权限：知识库路径加进 `permissions.allow` 的 `Edit(...)`、`Write(...)`，以及 `permissions.additionalDirectories`；
- 用户级 `CLAUDE.md` 里一行 `@<知识库>/维护约定.md` 导入维护约定。

`python install.py <知识库文件夹>` 依次做：
1. 目标文件夹不存在或是空的才继续，否则停下并说明原因。
2. 复制 `模板/` 和 `工具/` 里运行需要的文件进去；`git init`，**不设远程**，做第一次提交。这样使用者的知识库从一开始就和公开仓库没有关系，避免私人笔记被误推。
3. 修改 Claude Code 用户设置 `settings.json`：先备份成 `settings.json.bak-<时间>`；追加上面两个钩子（命令写成"当前 Python 解释器的绝对路径 + 知识库里的钩子脚本绝对路径"）和权限；已有同样的条目就不重复加。读不出 JSON 时一律不动，改为打印一段让使用者手动粘贴的内容。
4. 在用户级 `CLAUDE.md` 末尾追加导入那一行（已经有就跳过；改之前同样备份）。
5. 生成一次网页，打印"打开 xxx/学习台.html"和接下来该做什么。

另外三个参数：
- `--dry-run`：只打印会改哪些文件、改成什么样，什么都不写。
- `--uninstall <文件夹>`：把这个知识库对应的钩子、权限、导入行从设置里去掉（同样先备份），不删知识库本身。
- `--update <文件夹>`：用仓库里新的 `工具/` 替换知识库里的 `工具/`，不碰笔记和配置。
- `--claude-dir <目录>`：指定 Claude 设置所在的目录（默认 `~/.claude`），测试时指向临时目录。

安装时只问一个问题：**这个知识库主要用来做什么**，"自学"还是"工作上手、了解项目"【定：由使用者自己选，作者 11-12 提的，因为有人只拿它来学习】。也可以用 `--use study` / `--use work` 直接给出，不问。
- 选"自学"：问题表不分"问谁"（配置里 `问谁` 为空），不建 `工作.md`，网页上没有"工作"页。
- 选"工作"：问题表按"自己 / 同事 / 上级"分列，建 `工作.md`。
- 以后想换，改配置文件、加上或删掉 `工作.md` 就行，教程里写怎么改。
其余口径用默认值，装好后改配置文件。

## 六、从原版要改什么

1. **路径不写死**：钩子找知识库根目录的方式改成"钩子脚本所在的 `工具/` 的上一级"；原版已经支持用环境变量 `KB_ROOT` 覆盖，保留。原版允许笔记链接到知识库外的文件（比如代码仓库里的文档），范围是知识库的上一级目录；改成配置项"代码根目录"，默认还是知识库的上一级。
2. **配置文件 `学习台配置.json`**（放在知识库根目录）：
   - `问谁`：由安装时选的用途决定（见第五节），工作用途是 `["自己", "同事", "上级"]`，问题表按它校验，问题页按它分列；**为空表示不分"问谁"**：问题表不要求有这一列，问题页把待解决的问题放在一列里；
   - `工作.md` 变成可选：没有这个文件时网页不显示"工作"页，也不算格式错误【Claude 的判断，理由同上：只学习的人没有工作记录】；
   - `问题编号前缀`：默认 T 技术、B 业务、Q 思考、L 学习方法；会话启动提示报每个前缀当前的最大编号；
   - `代码根目录`：见上一条。
   - 成果类型、工作类型的可选值不做成配置，沿用原版（笔记 / 图 / 分析 / 数据 / 代码 / 其他；需求 / 排查 / 评审 / 运维 / 其他）。
   - 配置文件缺失、读不出或某项写错：按默认值处理，在网页的格式提示里加一条说明，不报错退出。
3. **计划**：原版的"成长计划"改名为可选的 `计划/总计划.md`，显示在计划页左栏；会话启动提示里的"本周"那一行读它的「进度表」小节（格式沿用原版：第一列写 `MM-DD 至 MM-DD`，`〃` 表示同上一行；以"计划""节点"开头的列会被带进提示）。没有这个文件或没有进度表，就不显示"本周"那一行，不算错误。`计划/` 下不是日期命名的文件都不当成每日记录（原版只特殊处理了一个文件名）。
4. **文案**：去掉页面和启动提示里专属于原作者的说法（对具体某个人的称呼和头衔、"每周交流"、成长计划等），副标题改成通用的；品牌名"学习台 · 个人知识库"保留。
5. **测试**：fixture 和测试里原作者的项目名改成"示例项目"，需求编号、带有原业务色彩的词换成中性的；全部测试通过。
6. **钩子日志**：自动提交失败时，把 git 的报错原文记进 `hook.log`（原版只记了"commit failed"，出了问题查不了原因）【Claude 的判断】。
7. 去掉原作者的一切个人信息：本机路径、名字、入职日期、设计文档里的背景。

## 七、模板里的维护约定

这是这个工具真正的"大脑"：Claude 每个会话都会读它，照着它边聊边记。从原版通用化而来，五节：

1. **我是谁、怎么教我**：上半部分留空让使用者填（身份、背景、在学什么、对讲法的偏好）；下半部分是一套默认讲法，使用者可以改：先查后讲、给出处（`文件:行号`）；证据分可信度；先打比方再展开，专业词第一次出现用大白话讲清；读一段流程时先看主干、再拆步骤、最后问为什么这样设计；讲完自己挑两三个值得想的问题讲透；先猜再查（使用者先预测，再由数据说了算，猜错的地方记成"我以为 / 实际 / 为什么"）；讲得出来才算掌握。
2. **知识库结构与格式**：几乎照搬原版第二节（骨架、主题笔记、知识点、概念卡、计划、三张表的格式，三层粒度，跳转规矩，相对路径，"所属"写法，问题编号），例子换成示例项目。
3. **边聊边记**：照搬原版第三节的通用部分：只有主会话记录、子代理不写；知识库不是项目仓库，绝不顺手改当前项目仓库；写知识库只用 Edit / Write（只有它们会触发钩子）；弄懂了就补概念卡或笔记；卡住了先过三问再进问题表；勾今日计划；工作表；每次记录后在回答末尾用一行说"已记录：……"；要点；每日复盘；当天第一次对话先补前一天的缺口再起草计划；下班时补"搞懂了""卡在哪里"；不记什么；**绝对不能记密码、密钥、token、真实客户数据**，万一记进去了马上删并告诉使用者；整理时不改原意；多个会话同时开着时先读后改。
4. **计划怎么调整**：每日计划跟着总计划进度表的这一周排；偏差了就调后面几行，不赶也不拖；改目标先给使用者看。
5. **当前进度**：留空，由 Claude 随学习进展维护。

去掉原版里所有和原作者具体工作有关的条款（某个公司的代码规范、分支对齐、需求工作流、给上级的汇报口径等）。

## 八、示例知识库和教程

- **示例知识库**【定：虚构】：一个虚构的"网上书店"项目（下单、库存、支付回调之类）。内容是通用的技术常识，全部新写，不从原作者的知识库改写。规模：骨架 1 张（几个大块，故意留一两块空白，让覆盖率看得出来）、主题笔记 3–4 篇（带知识点）、概念卡 2–3 张、每日计划 3 天、问题 5 条左右、成果和工作各 2 条左右。仓库里附上生成好的 `示例/学习台.html`，双击就能看。
- **截图**只从示例知识库截。
- **README**：一句话说清是什么；一张截图；能帮你做什么（个人学习、新工作上手、了解一个项目三个场景）；十分钟上手（前提：Python 3.10+、git、Claude Code；几条命令）；目录说明；链接到教程。开头一段英文简介。
- **docs/教程.md**：
  1. 安装；
  2. 第一次对话：填"我是谁"，建第一个项目的骨架；
  3. 一天怎么用：早上起草计划、白天边学边记、下班复盘；
  4. 网页怎么看；
  5. 想改规则怎么改（维护约定、配置文件）；
  6. 常见问题：钩子没反应、网页没更新、自动提交失败、怎么更新、怎么卸载、为什么知识库不要推到公开仓库。
- **docs/格式说明.md**：每种文件的完整格式和例子（原版维护约定第二节的详细版）。

## 九、防泄露（底线）

- 新仓库从第一个提交开始，是全新的 git 历史；原作者的知识库仓库和它的历史一律不碰、不推。
- 从原版拷代码时逐个文件过；`hook.log`、`hook-status.json`、生成的网页、`__pycache__`、书签之类的个人页面、原版的设计文档都不带。
- **扫描词表**放在仓库外的本地备注里（不提交）：原雇主名、项目名、同事名、内部域名、需求编号、只在原业务里出现的专有词等。推送前对整个仓库**和全部 git 历史**各扫一遍，命中必须为 0。
- 词表怎么来【Claude 的判断】：Claude 先从原知识库里抽能找到的（项目名、各服务名、内部域名、需求编号、同事称呼、工作邮箱的域名、分支名前缀等）；作者补上 Claude 无从得知的（雇主正式名称和品牌名、知识库里没出现过的人名和内部代号），并确认词表列全了。**这一步放在拷任何代码之前**，之后每次往仓库加文件都用它扫。词表已起草，作者确认不用再补【定】。
- 提交作者用 GitHub 用户名和 GitHub 提供的 noreply 邮箱，`git init` 之后、第一个提交之前就写进**仓库自己的** git 配置，不改本机全局配置（全局配的是工作身份）。
- **先私有、后公开**【定】：作者在网页上建一个**私有**仓库，第一次推送推到它；GitHub Actions 在 3.10 和最新版上跑测试，全部通过后，把文件清单和扫描结果给作者过目，作者同意了才把仓库改成公开。改成公开时整段 git 历史一起公开，所以私有阶段的每个提交同样要过扫描。
- 推到私有仓库之前，同样先把文件清单和扫描结果给作者过目。
- 示例内容全部新写。

## 十、怎么验收

- 全部测试在 Python 3.10 和最新版上通过（私有仓库的 CI），再改成公开。
- 在临时目录里走一遍安装：`--claude-dir` 指向临时目录，检查 `settings.json` 和 `CLAUDE.md` 改得对、备份在；用模拟的钩子输入手动跑两个钩子，看到启动提示、网页重建、自动提交；再跑 `--uninstall`，设置恢复干净；`--dry-run` 什么都不写。
- 示例知识库生成的网页打开正常，0 条格式提示。
- 检验模板里的维护约定【Claude 的判断】：示例知识库的内容交给一个子代理来写，它只拿到模板的维护约定和一段模拟的学习对话，照约定记录；生成网页必须 0 条格式提示。这样能看出 Claude 照这份约定记出来的东西格式对不对。发布前不跑真实的 Claude 会话（要么得用单独的配置目录重新登录，要么可能连作者自己的钩子一起加载），真实效果靠发布后作者自己用来检验。
- 防泄露扫描命中 0。
- 作者照 README 在自己机器上看一遍示例网页、读一遍教程，觉得能看懂。

## 十一、留给实施者的

代码具体怎么改、测试怎么组织、安装时复制哪些文件、示例写什么内容、CI 怎么配、截图怎么做。
